# Kanban human gates

## When to Use

- The user asks which cards need them, why one card is stopped, parked or in `triage`, or how the running cards are doing.
- You must decide whether a stopped card is a human gate or a machine-recoverable stop.
- You are reading or changing the change-only human-gate alert.

Lifecycle repair, routing and the Card comment format live in the shared `kanban-sdlc-orchestration` skill; project lanes and policy live in the project skill, e.g. `the project policy skill (settings policy_skill)`. Read those before mutating anything. This skill is the board-state reading layer: what the columns mean, and which cards actually need a person.

Re-verify these facts against the installed `hermes_cli/kanban_db.py` when behaviour looks different: `schedule_task`, `unblock_task`, `block_task`, `_route_block`, `recompute_ready`, `_has_sticky_block`, `BLOCK_RECURRENCE_LIMIT`.

Cards that a test or smoke probe leaked onto the live board inflate the `blocked` count and look like gates. Identify, trace, and retire them with `references/leaked-fixture-cards.md`.

For the two recurring stale-record shapes — a merged card whose completion receipt is missing, and an approved-plan digest that no longer matches the live plan — follow `references/stale-record-repair.md`. Both are machine-recoverable; neither is a human gate.

A bare short hex the user asks about ("how is 5d7980") may be a Kanban card id prefix (`t_<8 hex>`), not a git SHA. When `git rev-parse` and the GitHub commits API both miss, search the boards (`grep -rl <hex> ~/.hermes/kanban/boards/*/logs ~/.hermes/kanban/boards/*/attachments`) before reporting it unknown.

## Fast pass: "what needs me?"

1. `hermes kanban --board <slug> stats --json` for per-status counts. Take totals here; `list --json` is a bounded window.
2. `hermes kanban --board <slug> list --status blocked`, then `--status scheduled`, then `--status triage`.
3. `hermes kanban --board <slug> diagnostics --json` for the stalled class.
4. Classify each card with the table below, then `show` only the cards you will report.
5. Re-probe every external wait named in a stored reason (CI run, PR, upstream permission) before reporting it, because a wait that cleared since the last tick is a recovery candidate, not a gate.

When the user also asks whether the gates are on the initiative review board, or why one never reached them, cross-check each stopped card against the plugin's `reviews.db` with `initiative-progress-review` → Auditing gate coverage on the Review board. An answered review item can end in a deferral that never touches the card, so a gate can look covered while its answer is undelivered.

Answer shape: group the cards by who acts, not by status. Use three headings: **Needs your decision** (with the exact reply wording that answers each gate), **Waiting on missing tooling** (name the card that owns each gap), and **Ready for recovery now**. Then add one line naming the dominant cause, and offer the recoveries the operator can do now. Generate the gate list from the reporter script in a scratch state dir with the window forced open, so the answer and the alert use one classifier.

When the user asks you to explain a gate card, collect its body, comments, parent intake and cited plan, but filter large JSON inside the tool call before printing: show the current state, review verdict, relevant user decisions and failed predicate; retain the full history for targeted reads. Read the Review item's latest version, answers and action receipts alongside the card, because an applied answer can merely unblock work without performing the external change its label asserts. Then re-verify each cited source line on `origin/main`, because the planner's evidence can be stale. Also read every addendum, production change and sibling-card decision dated after the block (an edge rule, a merged PR, a decision recorded on the parent). A later change often makes part of the gated deliverable moot, and that turns a high-risk question into a narrowing choice. When the gate asks the user to approve or review a document (a plan, an amendment, a report), put a Markdown link with the absolute vault path near the top, for example `[plan v1](<vault>/project/agents/tasks/<file>.md)`. The desktop app turns a link to a local path into a preview card, so the user can open the document with one click. A path in backticks is not clickable. Link the cycle file and any amendment the same way. Answer per card briefly in this order: what is stopped and what it holds up; the actual failed condition, not its status label; what was tried and what the user already decided; what each option does next, its effort/cost and risks; your recommendation and why. Put a requested approval/review document's absolute-path Markdown link first. Define jargon on first use, distinguish fresh live checks from receipt-only evidence, and state uncertainty. Include verified `file:line` evidence or a small dependency diagram only when it clarifies the cause. Include a narrowing or drop option when part of the deliverable no longer needs the decision; mark unmeasured costs rather than guessing. Number or letter the options so the user can answer with one token ("3", "1A + 2A", "withdraw it"); this user answers that way. When the gate is a CI timeout, per-file cap or runner-resource stop rule, test the worker's diagnosis against the exact-head PR CI run before you relay it. Split the failures into families. Find which test was running when a cap kill landed. Download the diagnostic run's artifacts and read them. Check whether the diagnosis harness caused its own symptom, and compare runner images (`references/ci-resource-gate-diagnosis.md`). A "slow machine" headline often hides one hanging test. When the evidence shows that an offered option targets the wrong symptom, recommend that option with a narrowed brief instead of relaying it unchanged. Label each claim as checked live or only read from the card.

**Finish the explanation before seeking or applying a decision.** When the user requests explanation first and forbids changes, remain read-only and deliver the causal explanation before offering execution. Keep the narrow predicate and GitHub checks in the foreground or batch them directly; do not make a small blocker explanation wait on a background architectural exploration and return only a promise to finish. If supplementary checks remain, give the verified explanation with that limit. Reconcile late results against newer reads and actions before presenting them, because a pre-change observation must not resurrect a resolved blocker.

Before you walk the user through a gate, read the card's Review item, not only the card: `reviews.db` (`<plugin data>/initiatives/reviews.db`, opened `?mode=ro`) has `items.status`, `item_versions` (question, `options_json`, `recommend`, `context`), `answers`, and `actions` (a `mark_auto` row records when the user handed the item to the agents). Report that status as the user's last Review action: `open` (unanswered), `answered` (name the option), `deferred`/`watching` (parked), or `auto`. An `auto` item is applied by the next initiatives review run (the configured initiatives review job; inspect its schedule with `hermes initiatives status`) with the recommended option, or the best one available. When your live evidence shows that the recommended option targets the wrong cause, the user's first step is to take the item back before that tick: the Review tab's take-back button, or `manual Dnn` in the review topic. Agents cannot unmark an item (`unmark_auto` refuses the `agent` surface), and an applied option starts a planner run on the wrong brief. Give the minutes left until the tick. Check every user instruction in the item's option text against the approved plan before you relay it. The generator paraphrases, so it can tell the user to type a value that the plan says the script generates, or the reverse. Where they differ, the plan wins, and you say so in the explanation.

**No Review item yet is usually filing lag, not a session-only gate.** Only the initiatives review run (the configured review job) turns a blocked card into a multiple-choice item, from the `gates.json` its wake gate writes that run. Deep-tier merge gates are the exception: the 2-minute filer `<merge-gate-job-id>` files them. Until then the card shows only in the live "Waiting on you" list (it reads the newest `**You:**` line), which has no options, so its only button is **Start session to resolve**. When `reviews.db` has no item for the card, compare the block time with the cron's `last_run_at` and the `gates.json` mtime. If the block came later, tell the user the multiple-choice item will appear at the next tick (give the minutes left) and that answering it there (Review tab or `Dnn A` in the review topic) delivers the decision with no session. Do not walk them through an attended session or offer to post the answer and unblock on their behalf for an approval that a Review option will carry. Exception: when the approved operation runs only in the interactive session (a live runtime swap or a gateway restart that no worker may run), the attended session *is* the step. Then the Review item's unblock option must not be answered before the run, because it sends the card to its reviewer with nothing installed. Follow "Walking the user through an attended live-operation gate" and deliver the answer through the executor only after the run. After the tick, read the item's `options_json`: an approval gate (for example a deep-tier merge) must carry `kanban_unblock` for the card, not a `defer` option labelled "merge in GitHub", because a deferral never reaches the card and skips the reviewer's exact-head check.

When the gate is a missing cloud permission, check the claim live before you relay it. Read the identity's roles (`gcloud projects get-iam-policy <p> --flatten='bindings[].members' --filter='bindings.members:<sa>@' --format='value(bindings.role)'`) and any filter that hides the data (for example `gcloud logging views list --bucket=_Default --location=global`). Sample what the broad option would expose: for Data Access logs, group a week of entries by `serviceName`/`methodName`. Then compare the added exposure with the roles the identity already holds. A read grant to an identity that already has project-wide admin roles adds little, and a narrower option that needs new code costs one more review round. Say plainly when no one ran an effective-access check.

When the user challenges a recommendation ("why not just X?"), reassess it on the merits. If the rule you defended protects less than it seemed (for example, the host already holds secrets of equal value), say so plainly and list what X really costs, together with the conditions that make X safe. Do not defend the earlier recommendation by habit.

## Gate classes

Default to automation. Classify the live cause, not the status or stored `block_kind`:

| Class | Live test | Who acts |
| --- | --- | --- |
| machine predicate | A dependency merged, CI passed, a cooldown expired, a defect landed, or a recorded user decision already answers the question | recovery operator |
| mechanical routing | The deliverable is unchanged, but a guard, phase, or direct-triage intake prevents the recorded next role from claiming | operator; unclear ownership goes to the orchestrator |
| mechanical closeout | Review and merge are durably complete, but exact PR metadata or ledger reconciliation is missing | operator, only when project policy authorizes deterministic closeout |
| automation defect | The outcome is decided, but no supported command or unattended path can execute it (e.g. a contract change, a live consent prompt) | report once and route a tooling card; not a user decision |
| repeated failure | The same root cause recurred after automatic restructuring (split or re-plan) also failed. A timeout or budget exhaustion that left a new committed checkpoint or newly passed gate is progress, not recurrence | human, with a full failure report |
| true human authority | A high-risk trigger in the project risk rubric applies (missing credential or permission with no honest fallback, production cutover, security/auth/secret change, irreversible data action, change to an approved product outcome, ambiguous active ownership) | human |
| orchestrator intake | A direct-triage card still needs specification, admission, graph reconciliation, or an unresolved decision | orchestrator, or human only for the unresolved decision |
| active lane | `ready`, `running`, `review`, or parent-gated `todo` with no broken guard | nobody |
| leaked fixture | A test or probe wrote the card to the live board: placeholder title, empty `created_by`, `initial_status` block, workspace in a temp/scratch dir. See `references/leaked-fixture-cards.md` | operator archives it after the creator stops; not a gate |

- Re-probe the stated prerequisite. A typed `needs_input` or `capability` reason is a historical claim, not proof that a human is still needed.
- Treat a recorded user decision as a cleared predicate when it exactly answers the named gate. Route the existing card automatically; do not ask twice.
- A bare "approved" does not answer a gate that offered several options (for example, full plan vs source only). Ask the user for the exact option before any transition that depends on it, because the downstream orchestrator cannot tell which scope was approved and will stop again.
- `triage` holds intake and breaker-routed cards. A mechanical loop can be recoverable through the supported route. A review round cap is decided by the reviewer under the project policy's round-cap rule; only an unresolved high-risk product choice is human-only.
- **Pick-one-of-three gates with a recommended default are automation candidates.** This user wants medium-risk choices automated, not relayed. When a gate reads "choose A, B or C; I recommend A" (round cap, one more bounded run, defer), do not just relay it. Propose a deterministic rule, and when the user agrees, encode it in the project policy, the deciding lane's `SOUL.md`, and the recovery cron prompt together. Then unblock each affected card with a reason that cites the rule. The deciding lane applies the rule; the operator never issues the verdict.
- Route a fully decided direct-triage card to the orchestrator for admission reconciliation, not directly to implementation.
- Never infer or choose a new owner during recovery. Restore only the lifecycle phase already recorded; send unclear ownership to the orchestrator, which decides it explicitly. Never turn routing into a mandate or tool grant.
- Classify by risk, not by category. Low- and medium-risk choices (plan approval, test removal under an approved plan, contract reclassification, upstream fallback, ownership reconciliation) are autonomous when the project policy has a risk rubric; only high-risk triggers and repeated failures reach the user.
- A recorded approval does not satisfy a live tool-enforced prompt (for example a protected-instruction write guard). Classify a card waiting only on such a prompt as an automation defect, not as a fresh decision request.
- **Test the artifact, not the permission record.** Before you classify a consent- or edit-parked card, check whether the named edit already landed. Diff the before/after copies (`profiles/*/skill-backups/<name>-<before|after-version>-*/SKILL.md`, or the plan text) line by line: every added line must be in the current file and every removed line absent. Do not compare whole-file hashes, because a later version bump on top of the edit changes the hash while keeping the edit. An interactive session often applies the edit without routing the card back, so a check for a "newer grant" reads high-risk forever. A landed edit is a machine predicate: comment the line-level evidence and `unblock` the card to its own lane, which resumes the interrupted phase. The landed edit does not settle a plan acceptance criterion that requires authentic interactive consent, and the resumed worker cannot certify that criterion itself (a run started by a task request is not an interactive operator session). Name that residual review risk to the user when you report the unblock.
- **Check the installed primitive before accepting "waits on repair card X".** A card blocked behind a tooling-repair card often does not need that repair. Read the block event payload and the installed functions before you report the dependency as real. Routes to `review` for a `local-only` card (no PR exists, so never invent `published_pr`):
  - `blocked` with newest block event `source_status: "review"` and parents done: plain `unblock` lands it in `review`. `unblock_task` has no `published_pr` check.
  - `ready` held by `respawn_guarded: active_pr` (a PR URL from another card in a comment): move it to `review`. The review lane returns before the `active_pr` check, so the guard never applies there.
  - `triage` or `ready`: the shared `kanban_triage_route.py` with `"completion_contract": "local-only"`, no `published_pr`, and `"implementer"` from the newest `review_requested` event. Pass the implementer whenever the card is assigned to its reviewer: `request_review` records the current assignee as implementer, so without it a later `request-changes` has no profile to route back to.
  - When a route tool itself refuses ("needs published_pr"), fix the tool's contract test-first, not the cards. A cron that hits the same tool refusal on every tick will otherwise route the gap to the orchestrator, which opens a repair graph.
- **Recommend withdrawal when a repair outlives its reason.** Before relaying a repeated-failure gate on a tooling or repair card, check whether the cards that motivated it are now `done`, and whether each review round finds one more field of the same kind (for example, "prove this snapshot is still current"). That pattern rarely converges. Offer, in order: withdraw as undelivered, narrow by deleting the failing exception, or one more bounded plan.
- **Weigh the tooling fix against the blocked deliverable before routing it.** When a card waits only on a live prompt that a human can answer in seconds (an interactive session clicking **Allow once**), offer that path first and name what it unblocks. A routed tooling card goes through the high-risk security planner and can grow into multi-card, upstream-gated work that still needs a human per operation and leaves the original PR blocked for days. Route the tooling card only in addition, never as the only exit.
- Separate delivered code from bookkeeping. A merged card with failed closeout metadata is a ledger problem, not unfinished implementation.

## Running-card health

For "how are the running tasks doing", check each `running`/`ready` card from the DB read-only and live state:

1. Run elapsed vs `max_runtime_seconds`, and heartbeat age plus whether `/proc/<worker_pid>` exists. A recent heartbeat proves only that the worker is alive, not that it is making progress: heartbeats come from the wrapper, so a worker hung on one LLM call keeps heartbeating every minute. Prove progress from the agent itself:
   - Find the run's session in `profiles/<lane>/logs/agent.log` with `grep "msg='work kanban task <card>'"`. That log interleaves every session of the lane, so filter all later lines by the session id it prints.
   - Compare that session's last line, the card log mtime (`kanban/boards/<board>/logs/<card>.log`), and `ps -o etime,time -p <pid>`. Minutes of wall time with near-zero CPU, no new session lines, and one open connection to the model proxy (`ss -tnp | grep <pid>`) is a stalled API call, not slow work.
   - Check what the run already did (cards created, links, comments) before recommending `reclaim`, so the next run's remaining work can be stated exactly.
   - Repeated `timed_out` runs with no new commit and `API call failed` / `No available targets for combo` lines in the lane log mean the lane's model has no quota. Every retry spends one attempt until `gave_up`. Before deciding between "pin to a working combo" and "wait for reset", check `ocx provider quota --json` for the exact provider the card is pinned to (`task.provider_override`/`model_override`): a non-Codex provider (e.g. `google-antigravity`) reports its own `customWindows` with a per-window `resetAt`, separate from Codex's `fiveHourPercent`/`weeklyPercent`. A window minutes to low-tens-of-minutes from reset is a genuine, self-clearing quota wall — report the wait and let `respawn_guarded: rate_limit_cooldown` clear on its own; pinning to a different combo here only helps if you are willing to accept reduced review independence or a different model family for that card. Reserve pinning/`set-model` for when the matching window shows no imminent reset, or when the symptom is actually the dead-route/stale-token case (no provider reports headroom soon). Before pinning, probe the candidate combo under the lane's own profile (`hermes -p <lane> chat -Q -q "Reply with exactly: OK" -m <combo> --provider <provider>`). Then run `set-model <card> <combo> --provider <provider>` and `unblock --reason`, and confirm `API call #` lines for the new session in the lane log within a minute. Clear the pin (`set-model <card> none`) once the card is done, and say so in the report. Report this cause even from a read-only monitor tick: a monitor that reports only "still running" hides it for hours.
2. Worktree `git log -1` and `git status --short | wc -l`. Large uncommitted work near the runtime cap is **at risk**: a timeout before commit leaves nothing pushed. If the task's `max_retries` is 1, the timeout goes straight to `gave_up` and the card becomes `blocked`.
3. Prior run outcomes (`crashed`, `timed_out`, `gave_up`, `blocked`) and the last comment, for the worker's own progress claim.
4. `journalctl --user --since "-2 hours" | grep -E 'hermes-worker-kanban-<card>-run-.*(oom|Failed)'`. Each run has its own systemd scope, so this proves an OOM kill directly. A `pid not alive` crash or an rc=0 protocol violation without such a line has a different cause.
5. A `ready` or `review` card that does not start has one of three dispatch-level causes. Check them in this order before calling the card stuck:
   1. **Global emergency stop.** Read the sentinel `$HERMES_ROOT/ESTOP` (root home, not the profile; JSON with `engaged_at` and `reason`). `hermes pause` has no status verb, so the file is the readback. While it exists the gateway dispatcher skips every tick and resets its stuck counter, so the log goes quiet. `dispatch --dry-run` ignores the sentinel and still lists cards under `spawned`, so a dry run cannot prove that a spawn will happen. Find who engaged it and what lifts it: `ps` for a resume/refresh wrapper, and grep the cron `jobs.json` files for the reason text. Report the pause and its expected lift. Do not run `hermes resume` without the user's go-ahead, because it restarts cron and all dispatch fleet-wide while the protected job still runs.
   2. **Cap saturation.** Count `running` cards against `kanban.max_in_progress` (and the per-profile cap). The gateway logs `kanban dispatcher stuck: ready queue non-empty … 0 workers spawned … check profile health`. That text blames venv/PATH, but a full cap produces the same warning. Read the running count before chasing profile health.
   3. **Respawn guard.** Read `respawn_guarded` and `skipped_*` from the dry run.
   A slot freed by a timeout or crash only helps when no pause is engaged; re-read the board about a minute later to see whether a claim landed.

For "how are the cards in review doing", `review` is a queue for the reviewer lane, not proof that review is running. For each card, check whether a reviewer run is claimed now (`runs <id> --json`, newest run). Read the event that put it in `review` (approval relay, recovery routing, or a crash-recovery unblock) and the live PR head checks with `gh pr view <n> --json headRefOid,mergeStateStatus,statusCheckRollup`. A `SKIPPED` required job is not green, and a job still running is pending. If no reviewer is claimed, apply step 5's dispatch causes.

Before calling a check a gate, read the workflow's own condition: a job guarded by a literal `if: false`, or by a main-push-only / event-specific condition, will never report on this event, so a PR can never satisfy it and no amount of waiting changes that. Treat such a lane as not-run, not pending, and do not let a worker wait inside its run for a lane that cannot execute — hand off with the fast checks green and say plainly that the lane did not run. When required checks sit queued, name the holder before acting: `gh run list --status in_progress` identifies the branch, and a deliberate dispatch on another card's head is legitimate in-progress verification, not a stale run. Cancel only a superseded run for an older SHA of the same branch; cancelling another card's live verification destroys evidence and is never a scheduling fix.

Report one row per card: state, elapsed/limit, an assessment (on track / at risk / problem), and the one changed strategy that would fix it. For a near-complete card that timed out, unblock it with a publish-only strategy: verify the existing diff against the approved plan, rerun only the focused test, commit, push, and open the PR. Do not rerun full suites in the worker, because they used up the budget and exact-HEAD CI runs them anyway.

## Reading a stopped card

1. `hermes kanban --board <slug> show <id>` — the authoritative view: status, assignee, workspace, parents, comments, events, runs.
2. `hermes kanban --board <slug> runs <id> --json` — attempts; the newest run's summary carries the reason.
3. `hermes kanban --board <slug> dispatch --dry-run --json` — proves whether anything would spawn, and prints `respawn_guarded` reasons.
4. Read `block_kind`, `block_recurrences` and event payloads from the DB read-only (`file:<board>.db?mode=ro`); the JSON commands omit them. Run `PRAGMA table_info(tasks)` first, because column names vary by release.

Before reporting a human gate, exhaust these paths in order:

1. Prove whether the external predicate cleared.
2. Search the card for an exact user or approved-plan decision that already answers it.
3. Check supported same-card phase routing and guard repair.
4. Check policy-authorized deterministic ledger closeout after durable review and merge.
5. Check whether the remaining choice is low/medium risk under the project rubric; if so, route it to the role that decides it (orchestrator or reviewer) instead of the user.

Report four things: the recorded reason, whether it holds now, the automatic action available, and the exact human action only if automation ends.

For a repeated failure, the human report must carry: card, branch, PR, full SHA, failed phase, observed error, likely cause, first strategy, changed strategy, recurrence evidence, live ownership/process state, one recommended action, and at most three choices. Never retry silently a third time.

## Reviewing a recovery cron tick

For "review the last recovery run", "review recent recovery runs" or "why are cards still blocked after it ran", follow `references/recovery-cron-review.md`. It proves what the ticks did from the session transcripts, execution records and board events (the cron output file shows only the final report). It also covers the prompt rules that stop repeat comments and refused tool calls, and re-classifies each reported card from live state.

## Facts that decide the answer

- `scheduled` is a park, not a queue slot: no claim, and no timer expires it. `schedule_task` keeps `block_kind`, `block_recurrences` and the run summary, so a card can read `scheduled` in the status column while its recorded reason says BLOCKED. Report the status and the reason as two separate fields.
- Nothing releases a `scheduled` card automatically. `unblock` (CLI, or the dashboard's `Blocked → Ready`) is its only exit, and it always lands `scheduled` in `ready` (or `todo` while parents are open). Only a `blocked` card can unblock straight to `review`, from its block event's `source_status`.
- A parked card cannot be re-filed as `blocked`: `block_task` accepts only `running`/`ready`, and the dashboard's Blocked verb calls the same function. The only route is `unblock` → `ready` → `block`, which spends a recurrence.
- Same-kind re-block increments `block_recurrences`. At the limit the card moves to `triage` with `block_loop_detected`. `triage` has no *CLI verb* exit and no park: `promote` takes `todo`/`blocked`, `unblock` takes `blocked`/`scheduled`, `schedule` takes `todo`/`ready`/`running`/`blocked` (so `scheduled` is unreachable from `triage`), and `complete` refuses it as `unknown id or terminal state`. Its exit is the **field-free status transition** — call the primitive the `specify` verb wraps with no field arguments, which flips `triage` → `todo` and leaves the approved title, body and digest byte-identical:
  ```python
  import sys; sys.path.insert(0, "<hermes-agent root>")
  from hermes_cli import kanban_db as kb, kanban_db_connect as kbc
  with kbc.connect_closing(board="<slug>") as conn:
      kb.specify_triage_task(conn, "<card>")   # no title/body/assignee => status-only
  ```
  Pass `board=` explicitly, because without it the connection opens the current default board, not the card's. A `triage` card is usually assigned to the orchestrator: when the recorded decision names the implementer, `assign <card> <implementer>` first. It then lands in `todo` and is promoted and claimed within a minute. Run it under the dispatcher-owning profile's `HERMES_HOME` and interpreter, and confirm the installed signature before use. Prefer this over both alternatives: the `specify` *verb* runs an LLM that rewrites the approved title and body (so a card whose body is the contract must copy it first, or avoid the verb), and the temporary loopback dashboard route in `kanban-sdlc-orchestration/references/recovery.md` is the fallback for when no such surface is available. Read the landed status back before the next transition — the dispatcher may promote it onward, and a card whose runs were claimed from `review` lands back in `review`, not `todo`.
- A card comment cannot widen a lane mandate. Authority comes from the lane's `SOUL.md`. Unblocking a `capability`-blocked card before the mandate changes re-blocks within about a minute and spends one recurrence toward the limit. Fix the cause, then unblock once (see Applying a lane mandate change).

## "Why didn't the recovery cron release X?"

Answer from the cron's own reasoning, not from a guess. Search the job's transcripts for the card (`references/recovery-cron-review.md` → Tracing one card across ticks). Then name the rule chain that holds the card, in order: the plan decision, the policy line, and the cron prompt rule. Quote one tick's classification as proof. When the gate is a recurring user approval that a policy rubric already rates medium risk (for example a per-batch removal matrix), offer delegation to an agent lane as a user decision. Do not change anything before the user says yes.

## Delegating a recurring user gate to an agent lane

Use when the user moves a repeated approval (one per batch or per card) from themselves to a lane such as `project-reviewer`. One file that still says "user approval" keeps the lane blocking, so change every carrier in one pass:

1. Back up every file you will touch under `profiles/<active>/skill-backups/<slug>-<UTC>/`: the plan, the card map, the policy skill, the related method skills, **both** lane `SOUL.md` files (the approver and the handing-off lane), the cycle file, and each affected card body (`show --json` → `.body`).
2. Grep for the gate wording in the plan, the policy, method skills, the lane SOULs and the cron prompts (`user approval`, `approves`, `matrix`, `needs_input`). Card bodies carry their own copy too.
3. Ask with `clarify` about in-flight items before you edit: an item the user already approved can keep that approval or move to the new approver. Recommend keeping it.
4. Plan: append an amendment section (new decision id, `amends:` with the prior digest, the new route, what stays user-only, what is unchanged). Add a pointer on the amended decision row. Write the new `<plan>.md.sha256`. Update the card-map rows.
5. Route on the same card with existing primitives. Check them in the installed `kanban_db.py` before you write the route: `request_review` accepts a card with no PR; `request_changes` returns the card to the implementer from the newest `review_requested` event. The approver answers in the `request_changes` reason with a fixed verdict prefix and the full digest, so the implementer can check that it implements the approved bytes.
6. Keep explicit user-only exits: a high-risk trigger, a change to a keeper or contract the plan names, missing remaining proof, and a round limit. Rewrite any card text that says "unless the user's approval says otherwise" to "the approver blocks for the user".
7. Policy skill: add the delegated route next to the user route and bump the version. Approver SOUL: add a section with the verdict format, and "do not `kanban_complete` for this phase". Implementer SOUL: add the handoff exception.
8. Card bodies: build each new body in Python from the saved body, with `assert body.count(old) == 1` for every replacement and an assert that the old gate text is gone. Apply with `edit <id> --body`, then read each body back and compare it byte for byte.
9. Record the user decisions on the cycle (`by: user`, session id), validate, and only then unblock the in-flight card with the approval and the re-read artifact digest in the reason. Read back the claim.
10. Report that the new route has not run yet, and name the first card that will exercise it.

## Applying a lane mandate change

Use when the user approves a mandate edit that a blocked card names ("apply the mandate"). The edit alone rarely unblocks the card, because the card usually carries admission prerequisites as well.

1. Re-read the card: status, `block_kind`, `block_recurrences` (compare with `BLOCK_RECURRENCE_LIMIT`), no claim or run. Take the exact scope from the comment that proposed the edit.
2. Back up `profiles/<lane>/SOUL.md` under `profiles/<active>/skill-backups/<lane>-SOUL-<UTC>/`, and record its SHA-256.
3. Append a card-scoped section, not a rewrite of the general rules: the authority (user decision plus the proposing comment), the card id and approved-plan digest, an end condition (card done or archived), the allowed targets and operations, "admission readback first, block and name the missing item", the per-operation record (target, limit, stop condition, rollback), and the limits that stay in force. Leave the general mandate unchanged for every other card.
4. Read back the new SHA-256 and the section.
5. Before you unblock, check every admission prerequisite the card names, read-only. For a deploy-gated operation, check the workflow job condition (a literal `if: false && …` is a hard-off), `gh secret list` for the repo **and** for each environment (`gh api repos/<o>/<r>/environments`, then `gh secret list --env <e>`), repo variables, and the host commissioning notes in the plan vault.
6. If a prerequisite is missing, park the card with `schedule <id> "<missing prerequisites; release condition>"` in the same step as the edit. Do not leave it `blocked`: the recovery cron reads the applied mandate as a cleared predicate and unblocks (and reassigns) the card within one tick, even when a newer comment lists the gaps. Post `BLOCKED — NEEDS YOU` with the applied mandate (old and new SHA, backup path), each missing prerequisite with its source line, and the next gate, which is usually a separate commissioning plan. A same-kind re-block at the recurrence limit sends the card to `triage`.
7. If every prerequisite holds, reassign only when the proposing comment names the owner. Then `unblock --reason`, and read back a fresh claim.

Offer the user two exits for a missing prerequisite: approve the commissioning gate, or narrow the card to the operations that need no missing prerequisite.

When the user picks the commissioning gate:

1. Re-read the parked card. If the cron already re-queued it and no claim exists, `schedule` it again and comment why.
2. Search for an existing plan card by idempotency key and title. Derive the key from the parent plan's key family (`<family>:<plan digest>:<slug>-plan`).
3. Write the body to a scratch file and create one planner card with `--body-file`, `--assignee <planner lane>`, `--workspace worktree:<repo>`, `--idempotency-key`, `--max-runtime 86400` (backstop only), `--created-by <operator>`, and the policy skills. The body states: the plan file path, the verified gaps with source lines, the source documents with SHA-256, what the plan must cover (secrets entered by the user only, host readiness, the exact interlock change and its rollback, the first release that produces the receipts, the delivery-card split), out of scope, the risk class with its high trigger (so the user, not the reviewer, approves), and "orchestrator links the delivery cards as parents of the parked card; release it only after they are done".
4. Subscribe the user to the plan card: copy `platform`, `chat_id`, `user_id`, `chat_type`, `notifier_profile` and `delivery_mode` from the newest `notify-list --json` row for the same user, then read the row back.
5. Comment on the parked card with the plan card id and the release condition.

## Explaining or cancelling a card graph

For "why is X taking so long", answer with a time breakdown, not a status line. List `runs <id>` with the elapsed time of each run. Separate wasted runs (reclaimed, looped, overwrote approved inputs) from productive ones. Split the live run's time from `log <id> --tail 15000` into recovery, implementation, local gates (pre-push hook) and CI wait. Then compare the diff size (`gh pr view <n> --json additions,deletions,changedFiles`) with what the symptom needs. Users ask this when they suspect over-engineering. If the scope is out of proportion, say so and offer the smaller fix. When you explain what the card does, say whether an ops or host step is still needed after the merge: a guard-only PR turns a silent failure into a loud one but does not make the feature work.

For "what is X working on" or "why is this task needed", walk the lineage before judging it: `show` the card, then its `parents`/`children` and the intake card's body, plus any approved-plan attachment. Report the originating deliverable, the chain that leads to it, and progress from the worktree (`git log <baseline>..HEAD`, `git status --short`), not from the card body alone. State plainly when the cost of the chain is out of proportion to what it unblocks, and give a cheaper path.

When the user cancels a graph, apply this order. Each step stops a worker from claiming work you are taking away:

1. Re-read every card's status, then `reclaim <running-card> --reason "<user decision>"`. Confirm the worker PID is gone or `<defunct>`, and confirm that `runs` shows `reclaimed`.
2. `archive` every cancelled card, including the `todo`/`blocked` descendants that exist only for it.
3. Park the downstream card that the cancelled cards gated (`block --kind needs_input "<next human path>"`) **before** you `unlink` its edges. Unlinking first makes it immediately runnable, and it can then fail headless again. A card with earlier same-kind recurrences can land in `triage` (`block_loop_detected`). That is still a valid park, so report it as triage.
4. `unlink <cancelled> <downstream>` for each edge, and leave the historical planning edges alone.
5. Comment on each archived card: the user decision, "do not recreate", the preserved branch and commit, and what never happened (push, PR, grants, installs).
6. Read back the status and parents of every card, plus the live processes, then report one row per card with before and after.

To withdraw a single repair card as undelivered (user decision):

1. Prove no claim, run, PID or task-owned process, and no children.
2. Preserve the candidate before `archive`. Archive cleanup keeps a `worktree` workspace whose commits are local-only, but it deletes a `scratch` workspace. For a scratch card, write `git bundle create <archive>/<card>-<sha8>.bundle HEAD` from the workspace's source repo into `profiles/<operator>/archives/kanban/<card>/`, then `git bundle verify` and record its SHA-256.
3. Post a `**WITHDRAWN**` comment: the decision, why, final candidate SHA, the open finding, where the candidate is preserved, and "nothing installed". Then `archive`.
4. Release each dependent with the routes above, and read back the landed status and a fresh claim.
5. Remove the reason the repair was created in the same step. Fix the cron prompt, the route tool and the shared recovery reference that sent cards to it, and state in the prompt that no repair card for this gap may be created. Withdrawing only the card lets the orchestrator open a fresh repair graph for the same gap within hours.

## Relaying a gate answer to a blocked planning card

When the user answers a `needs_input` gate on a planning card, the unblock reason is the planner's new brief. Write it so the next run needs no further question:

1. Re-read the card: status, block event `source_status`, no claim, run, PID or task-owned process, clean worktree, parents done. In the `/proc` scan, catch `OSError` per process and skip it, because some `environ` files are root-only. A crashed scan proves nothing, so rerun it before you report the transition as safe.
2. Write the reason to a scratch file in the Card comment format: headline with the decision, `**Next:**` naming the planner and the approver. In the body list what the next plan version **removes** (sections, fields, flags, report counts), what it **keeps** unchanged, any new prohibitions the decision implies, and any known limit to document (for example, historical data the narrowed plan will not correct).
3. Re-classify the risk after the narrowing. When no high-risk trigger remains, say that `project-reviewer` (the policy's independent approver) approves the next version, so the user is not asked again.
4. When the answer reverses a rule in an approved plan, label it as a plan amendment and give the reason. Never edit the approved plan file: re-hash it so the approved digest still matches. If no card pins the receipt's digest, append the amendment to the approval receipt as `Amendment N`. If a card body pins the receipt's SHA-256 too, write the amendment as a separate vault file with its own `.sha256` sidecar instead, because appending breaks the receipt digest that the worker verifies before every step. Point the card comment at the amendment. When the answer gives a worker access it lacked (a test host, a tool), put the exact access command on the card, using an existing identity. Also put the limits there: resource name prefix, cleanup, loopback-only ports, and what not to touch. A comment that grants access without a working command makes the worker block again. When you executed part of the answer yourself (for example, you created a service account or a key), put its identity, scope, storage path, test result and handling rules in the Evidence section. Say "already exists; do not create another", so the plan covers only installing and verifying it. Never put a secret value or a full key id on the card.
5. Tell the planner to keep the earlier draft and attachment as history and to write the next version as a new file and attachment. If the parent intake card is `done` and its title still names the dropped part, say "do not reopen the parent".
6. `unblock <id> --reason "$(cat <file>)"`, then read back the landed status. With the host running-cap full, report `ready` as queued, not started.

## Applying a Review answer in an interactive session

Use when the user answers an open Review item (`Dnn`) in chat, and the option needs an operator action outside the card (an IAM grant, a config change) before the card can resume.

Distinguish an option answer from a direct instruction to change a named external setting. If the user authorizes only that setting while withholding card, Review or file changes, perform only the authorized operation after its required preflight and readback; do not silently run this whole application sequence. Preserve any separate approval or amendment requirement, and report the still-open reviewer/ledger step. A settings write, a Review answer, an unblock and independent completion are four different effects; never claim one proves the others.

1. Confirm the production mutation with `clarify` before you run it. One question lists every step: the amendment, the exact command, and the Review answer. Add the one-line rollback. A bare option letter approves the option, not the operator acting on production.
2. Write the plan amendment as a new vault file `<date>-<plan-slug>-amendment-vN-<dnn>.md`, with front matter (`amends_plan_sha256`, `approved_by: user`, the session id) and sections for the problem, what it adds (the command, the readback and the rollback), the accepted exposure, and what stays unchanged. Write its `.sha256` sidecar. Never edit the approved plan, because the card checks that digest.
3. Apply the mutation with a before/after proof. Save the full policy before the change to scratch. Diff the bindings as `(role, member, condition)` sets after the change. The proof is exactly one binding added, none removed, and `auditConfigs` unchanged. Read back the identity's roles.
4. Record the decision on the cycle under `decisions:` (`by: user`, `review: Dnn`, session id, amendment path and SHA-256). Run `validate_initiatives.py`.
5. Post an `**FYI**` card comment: the headline says the finding is resolved, and `**Next:**` names the lane that resumes. In Evidence, give the amendment digest, the command, the diff result, the rollback, and a note that tells the reviewer the finding is closed by the amendment. Use `PR #<n>`, not a PR URL.
6. Deliver the answer through the Review executor, not with a bare `kanban unblock`: `python3 <initiatives skill>/scripts/daily_review.py answer "Dnn A"`. The executor records the answer in `reviews.db`, posts the decision header and unblocks the card. A direct unblock leaves the item `open`, so the next tick asks again.
7. Read back the card status. Then check the dispatcher's causes (ESTOP, cap, guard). With the cap full, report `ready` as queued, not started. Name the residual risk: a permission grant has no effective-access proof until the first real run.

## Releasing a card parked on third-party permission

Use when a card is parked on purpose until an outside party (a site owner, a vendor) grants written permission, and the user says the permission arrived.

1. **Check the evidence before you record anything.** Look for the reply in the vault, on the card's attachments and in `~/Downloads`. Compare its scope with every use the card performs, one row per use (for example: automated reads, sending the text to an outside AI service, showing quotes on a commercial site). Show the user that table. A reply that covers only part of it counts as narrower permission under the plan.
2. **When the user asserts permission without the document, or tells you to just proceed**, do not unblock on the bare statement. The worker re-checks the release condition and stops again. Ask one `clarify` with these options: (a) amend and release on the user's word, with the user accepting the uncovered uses as their own risk; (b) the user saves the reply to the vault first; (c) record the narrower scope and route the card to the planner. Never ask the user to paste the reply into chat; have them save it to a named vault path.
3. **For (a):** write a separate amendment file, because the card pins the receipt digest. Give it front matter (`amends_receipt_sha256`, `plan_sha256`, `approved_by: user`, session, card, cycle) and these sections:
   - **Decision.** Say plainly that the permission was given on the user's word and no document is attached.
   - **What it amends.** The release condition it replaces.
   - **The owner's condition, turned into stop rules.** For example, "must not harm the site" becomes: stop and block on any 429, a run of 5xx errors, a challenge page or a slowdown, and never retry faster.
   - **Unchanged.** The other release conditions, every must-not, and any later publication or production gate.
   - **Residual risk the user accepts.** Then write the `.sha256` sidecar and re-hash the plan and the receipt.
4. Add a `by: user` decision row to the cycle (amendment path and SHA-256, session id). Run `validate_initiatives.py`.
5. Re-read the card, then `unblock --reason`. A card whose parent is still open lands in `todo` and waits. Report that, not "started". If the card has no Review item, a direct unblock is the only release route. Then post an `**FYI**` receipt comment using the pre-post length check from Pitfalls.
6. **"Unblock everything" means every card actually stopped.** Read each sibling's status first. A sibling that is already `ready` or running needs nothing, so name it and leave it alone. Do not invent transitions to satisfy the wording.

## Walking the user through an attended live-operation gate

Use when the user must approve a receipt or plan whose live steps only the interactive session may run (runtime or source replacement, a service stop, a channel write), and has asked to be walked through it.

1. **Identify the approved bytes by hash, not by filename.** Re-hash every attachment the reviewer's verdict names (`sha256sum` over the card's attachment dir) and link the file whose hash matches. Re-uploads under the same name are stored with ` (1)`/` (2)` suffixes, and the unsuffixed file is often the stale version.
2. **Re-run the receipt's baseline read-only:** HEAD, the pinned diff hash, the launcher hash, the candidate ref (`git ls-remote`), service MainPIDs, lock holders, timer next-elapse, disk, stash count, and the absence of the files and branches the run will create. On a partial (`blob:none` promisor) clone, set `GIT_NO_LAZY_FETCH=1` for every read-only git command. Otherwise a `diff` between two trees fetches packs into the live `.git`, and that write changes the object count and the abbreviation width of later hashed output.
3. **Check what downtime would interrupt:** the running Kanban workers (`list --status running`, their `hermes-worker-kanban-*` scopes), any operator-watched data run, and timers whose `Persistent=true` catch-up would fire when the run restarts them. Map each worker PID to its card with `tr '\0' '\n' </proc/<pid>/environ | grep HERMES_KANBAN_TASK`. Workers survive a gateway stop, but their code changes underneath them, so recommend a window after the long-running owners finish. When the running cap is full and `ready` cards are queued, a receipt rule of "wait until no workers remain" together with "never pause dispatch to make a quiet window" may never be satisfied, because a new claim replaces each finished worker. Name that conflict in the readiness table and offer the user two readings: wait for a natural gap (recommended), or let the update helper's own pause-and-drain count as meeting the rule, which means the backup and the source switch happen while workers are still running.
4. **Read the stop conditions against the steps.** A rule like "stop if `.git` changes between step X and Y" can contradict steps inside that range that write `.git` themselves. Name every such contradiction, and how you will read it, inside the approval option, so the user approves your reading and not only the document.
5. **Name the execution context the commands assume:** the working directory (`-m <module>` needs the checkout on `sys.path`), the pinned `HERMES_HOME` (the interactive session's own is a profile home), and a clean `PYTHONPATH`. Also check the session-bus and CLI environment the probes rely on: echo `XDG_RUNTIME_DIR` and `command -v gh` in the preamble. The agent's terminal shell can lack `XDG_RUNTIME_DIR` even when `DBUS_SESSION_BUS_ADDRESS` is set. Export `XDG_RUNTIME_DIR=/run/user/$(id -u)` before any `systemctl --user` step and record that in the receipt, because without it a `systemctl --user` call can fail in a way that looks like a unit failure. Export once at the top of every terminal call, because each call to the receipt's shell block starts from the session's snapshot environment, not the previous call's exports.
   **Read a "no newer release" predicate with the consumer's own classifier.** When a step requires that the updater sees no release (`update --check` must say explicitly that none is available), do not interpret the CLI wording yourself. Grep the helper that will act on it for its markers (for example `UPDATE_AVAILABLE = (...)` and its verdict-line prefixes). Compare today's output with that helper's recent `check:`/`outcome:` journal lines (`journalctl --user -u <update unit> -o cat | grep -E 'check:|outcome'`). Output that matches none of the markers and equals a past `restart-only`/`no-update` verdict counts as no release. Report the exact line and why it qualifies, because wording like "checkout is newer than the selected release" reads as ambiguous on its own.
6. **When the approved source SHA is behind current main, re-prove it rather than re-ask.** Run `git merge-base --is-ancestor <pinned> origin/main` and `git diff --stat <pinned> origin/main -- <every path the operation runs>`. Still an ancestor plus an empty diff means the approved SHA stands unchanged, so say that in the readiness table. Any diff in a named path is a stop: refresh the decision package, and do not substitute the newer SHA.
7. **Re-read the exposure or route capability live for a public-exposure gate** (a tunnel, a Funnel, a new listener). Check that the exact target port has no listener and no mapping. Check that the node's capability names that port (Tailscale: `tailscale status --json` → `Self.CapMap` `funnel-ports?ports=…`, plus `tailscale funnel status --json` `TCP`/`Web`/`AllowFunnel`). Check that the session user can run the change without sudo (`tailscale debug prefs` → `OperatorUser`). List the routes that already exist as excluded, so cleanup is target-specific and never a reset. Then check that the intended client can reach the proposed port at all, because a public probe from the host passes while the client's own egress refuses the port: ChatGPT custom connectors connect only to 443 (`cdp-web-app-automation` → `references/chatgpt-connectors.md`). A package that names a non-443 port for such a client must be refiled before attendance, not discovered at the client step.
   When the client step does fail on transport, the approved stop condition still governs: diagnose only while the user is present and asks for it, report the cause with controls, and offer cleanup first, because the public route stays live until torn down.
8. **When the gate re-runs a check that failed on a known defect, check whether the fix is in the pinned artifact.** A fix card that is `done` and merged on main does not change an image or release already pinned by digest. Run `git merge-base --is-ancestor <fix-merge> <pinned source sha>` for every pinned pair. If the fix is missing, the re-run would fail the same way, so give the user a proof path that avoids the defect, as the reviewer allows. Say this in the preflight before the user approves.
9. **Lay out the run in downtime-bounded checkpoints** (pre-downtime checks, stop, backups, source switch, prepare, start and acceptance), and stop for the user's go at each one. Offer lettered options: approve and run after the in-flight owners finish (recommended), approve and run now, or reject. For an exposure pilot, the checkpoints are: the user signs in; a private start with private probes; the public route with public probes before any client connects; the client run; cleanup with a readback showing the endpoint is dead; the receipt. Before each checkpoint you run, re-read the live preconditions it depends on (SHA ancestry, target port free, routes unchanged, slot free), because the user's readiness reply can come minutes or hours after the preflight. Save each probe's stdout and stderr, plus its exit code, to a private scratch evidence directory for that step, so the receipt comment cites files rather than chat text.

   **Check for a concurrent operator on shared state at every checkpoint.** Another session can deploy a plugin or restart a service in the middle of the window. A dashboard restart runs a dependency sync, and that sync changes the selected environment and dependency stamp that receipts pin as baseline, without any of your commands running. Signs: a new `~/.hermes/logs/update_receipts/pm_*-sync-*.json`, a newer mtime on `installs/<id>/facts.json`, a new `environments/<hash>`, and `Started`/`Stopping` lines in the user journal. Find the writer from the journal unit (`_SYSTEMD_USER_UNIT` of the sync PID) and from the plugin repo's `git log`. Find what changed with `diff -rq` between the old and new `environments/*/workspace` directories. A one-off "install out of sync" warning while that sync runs is the sync itself in progress: rerun the same probe once before you treat it as a finding. A new dependency stamp does not by itself mean new dependencies. The PM stamp (`pm/packages.py` `expected_stamp`) hashes `uv.lock`, the extras, the Python artifact and the enabled plugin-member set, so a plugin commit alone produces a new stamp and environment. Prove that the drift is benign before you present it: compare `sha256sum` of `workspace/pyproject.toml` and `workspace/uv.lock` in the old and new `environments/<hash>/`, and compare the sorted `site-packages/*.dist-info` lists, hashed. Then name the side effect the restart step will carry: find which environment each long-lived service actually runs (`grep -o '<installs>/[^ ]*environments/[0-9a-f]*' /proc/<pid>/maps | sort -u`). A gateway still on an older environment moves to the newly selected one, together with the new plugin commit, at the receipt's restart. If the receipt's live checks still pass (environment current, nothing pending), present a reading that accepts the routine drift and records the old and new values for the reviewer, or a stop for a receipt refresh. Pinned baseline values that a receipt calls immutable fall under its own "changed dependency/install record" stop rule, so a run-through grant does not cover them: stop and ask, even mid-run. Ask the user to hold deploys until the restart step finishes. Project mechanics (for the project, `the project policy skill (settings policy_skill)` → `references/interactive-operator.md` → Running an attended exposure pilot) carry the commands.
10. **Answer in this shape, which this user asks for:** the step and why it needs them; their last Review answer, its item status and the cycle decision row; what agents do before and after; a readiness table (each check ✅/❌, live); the numbered checkpoints. Then give only the current step with its exact actions, and end on one reply token ("signed in", "go 2", "stop"). When the user replies "go N and finish all" (or similar), that grants a run-through. Execute the remaining checkpoints without asking again. Still re-read each checkpoint's live preconditions, and stop and report only on a failed check, a stop rule, or a window too short for safe drain, restart and rollback. Give one short status per completed checkpoint, not a fresh approval prompt. A wait step (for example for workers to finish) runs as a background poll with completion notification (`terminal(background=true, notify=true)`), bounded so it ends before the latest safe start time. Compute that time from the next timer fire minus the helper's drain cap, restart wait and rollback, and tell the user. If the poll ends with work still running, relaunch it once with the remaining budget. End the turn with a one-line status rather than blocking on repeated waits. After a wait, re-run the full baseline probe set before the first writing checkpoint, not only the worker count, because a wait of an hour or more lets other sessions change pinned state. Before each of your own checkpoints, list what it writes and its stop or rollback rule. Never ask for a credential in chat; the user enters it on the site. Give the user only the steps that need a human: sign-in, 2FA and account-security prompts. Once they have signed in, drive account forms yourself in their signed-in browser (creating or removing a connector, a settings toggle), after their go for that checkpoint. This user asks "can you do it?" when handed a click list for a form the agent can drive.
11. After the run, record the decision on the cycle (`by: user`, session id, receipt digest), post a receipt comment, and deliver the answer through the review executor so the Review item closes. Then name the lane that resumes (usually the same-card reviewer, for the installed proof).

## Narrowing a live card (user scope change)

When the user narrows a card mid-flight, keep the same card, branch and PR. Do not archive it or create a replacement. A new card breaks graph provenance and loses the evidence.

1. Save the current body: `show <id> --json`, then keep `.body`.
2. Write a `## SCOPE CHANGE — user decision` section. State the new deliverable, what to remove from the branch (with a new commit, never a force-push), the test constraints, the new acceptance criteria, and explicit out-of-scope follow-ups. Add a reviewer note that voids the earlier findings tied to the dropped design. Without that note, round-2 review re-blocks on them.
3. `edit <id> --body "<section>\n---\n# ORIGINAL BODY (history)\n<old body>"`. Prepending keeps history and makes the new contract the first text the worker reads.
4. If a run is live, `reclaim <id> --reason "<user decision>"`. Otherwise the worker keeps spending its budget on the dropped design. The dispatcher re-claims the `ready` card in about a minute, and the new session reads the new body.
5. Post a decision comment in the Card comment format. Say what changed and who the next owner is. Say that uncommitted WIP from the stopped run is discarded, and which review findings are void.
6. Read back the new run in `runs <id>` and the new body head in `show <id>`.

## The change-only human-gate alert

Gate set and mechanics are in `kanban-sdlc-orchestration/references/operator-status.md`. Two things it does not state:

- The reporter must include breaker-routed `triage` cards (those with a `block_loop_detected` event); a reporter that reads only `blocked`/`scheduled` hides exactly the repeated failures the user wants to see. Direct-intake `triage` stays out.
- Silence is not an inventory. The reporter compares the current digest against the last notified one, so an empty payload means "unchanged", never "no gates". To answer the user, read the board.
- Silence also occurs outside the proactive-notification window, even when the gate set changed. To answer "why was it silent?", read the reporter's state directory: `history.jsonl` records `event` (`emitted`/`pending`/`unchanged`) and `allowed_window` for each tick, and `state.json` keeps `pending_digest`. `pending` with `allowed_window: false` means the change will be delivered on the first tick inside the window. A present `last-error.txt` means the reporter failed.
- A newer `BLOCKED — NEEDS YOU` comment replaces the stored block reason as the digest text, because the stored reason goes stale when the operator escalates (for example, a `transient` resume reason later escalated to a decision). Use only the comment's headline and `**You:**` line for the digest. The Evidence section carries tick times, so it would re-ping on every re-post.
- A card that changes gate class between ticks is reported as RESOLVED. Read that line before believing a gate cleared: a card that moved from `blocked` to `scheduled` or `triage` left the set without being answered.
- **A completion is not automatically alertable.** Notify only when the human has an action or a decision. A closeout that needs nothing — an `FYI`, an operator-authorized no-code closeout, a verification-only card, a reviewer approving work already merged — stays silent, because an update the human cannot act on trains them to ignore the channel. Read the verdict, not the event kind: `FYI` and `BLOCKED — MACHINE` are observational; `BLOCKED — NEEDS YOU`, a plan or merge gate, and a decision request notify.

## Pitfalls

- Do not call a card "blocked" or "scheduled" as if those were one field. Give the status and the reason.
- Do not unblock a card whose cause is still live. It re-blocks, spends a recurrence, and can land the card in `triage`, where the human's job only grows.
- Do not infer the gate set from a status filter alone: `blocked` alone and `triage` alone are each wrong in both directions.
- Do not report a `ready` card as queued work without checking its guard. `respawn_guarded: active_pr` or `stranded_in_ready` means a healthy dispatcher is deliberately holding it.
- Do not lift a respawn guard to make a card runnable; route through the lifecycle phase that satisfies the guard.
- Check a card comment before you post it, not after. Pass the body through argv from a Python `subprocess` list. Assert that the text above `---` is at most 600 characters (the Card comment format limit) and, on a card with an open PR, that it has no PR URL. The lint script only reports after the post, and a stored comment cannot be edited.
- Do not put a PR URL in an operator comment after a `changes_requested` handoff. `active_pr` scans the newest comment that has a PR URL within 24 h, and only an `assigned`/`changes_requested`/`review_reopened` event after that comment lifts it. A later guidance comment with the link re-arms the guard, and the implementer is not respawned. This includes a decision or correction comment that merely cites the PR. Name the PR as `PR #<n>` instead. To diagnose, compare the newest PR-URL comment time with the newest handoff event. Only a genuine cross-profile handoff lifts it: the guard treats an `assigned` event as a handoff only when its payload carries a `from` that differs from the new assignee, so a same-profile re-assign, an unassign, and the dispatcher's own `default_assignee` write do not count. To release a card you armed yourself, reassign it to a different profile and back to its owner; that also resets the failure counter, so count it as the card's one deliberate reset.
- Do not trust a diagnostic line in the gate alert (for example `repeated_crashes`) or the recovery cron's own block comment as the current cause. Both can predate later review rounds. Read the card's newest `respawn_guarded` events and the dispatcher guard code first, and correct a wrong cron comment on the card.
- When you clear one of several gates on a card, park it in `scheduled` in the same step if other gates remain, and say so in the first line of the comment. The recovery cron treats the cleared gate as a cleared predicate and unblocks the card within one tick, even when a newer comment lists the remaining gaps (the mandate procedure above applies this).
- Do not describe a closed or superseded PR as waiting for CI approval. Re-read the PR and name the new permission or rescoping decision.
- Do not broaden a recovery cron prompt beyond the policy skill it loads. Amend the policy, the lane `SOUL.md` files, and repo instruction files (`AGENTS.md`/`CLAUDE.md`) together with the prompt, because any one of them still saying "needs user approval" keeps lanes blocking. Grep all of them for `user approval`, `user decision`, `round` and `same root cause` before declaring the autonomy change done. Back up each file under `profiles/<active>/skill-backups/` first.
- Do not count a stale workspace claim as a gate after the installed resolver disproves it. Preserve the correction and classify only the remaining cause.
- **A repaired test that goes red on baseline is a product bug, not a test defect — and not automatically a human gate.** When making an old test honest exposes real misbehaviour, the card blocks `needs_input` with a reproduction. Check the approved plan before reporting it to the user: when the plan already fixes the disposition (for example, one card per product-bug item), the answer is recorded, so classify it as a machine predicate and route the bug to its own card. Keep the repaired test RED in its own commit; never let the repair card weaken the assertion or fix product logic to go green, and never revert the repaired test to its vacuous baseline form. The bug card then gates the repair card's merge, because those rows assert the correct behaviour — raise the bug card's priority so it lands first, and expect the repair card to rebase and go green with no assertion change. At handoff, name the RED rows and their owning card, or the reviewer reads them as an unresolved defect.
- **Do not ask a worker for a browser-level red on a timing-dependent bug.** A race (a late response overwriting state the user already changed) passes or fails by luck in a browser test and flakes in CI, so any red it produces is a coin flip. Require the reproduction at the component boundary with the response held and released, which is deterministic.
- **A stale server-slot holder blocks a card that needs a port pair.** Classify every listener before releasing a slot-blocked card: a live run keeps its slot, while residue — a `ready` card with no claim and no worker PID, or a worktree whose card is gone from the board — is stopped with the repo wrapper from that worktree's own root (`cd <worktree> && ./scripts/setup-worktree.sh --stop`), never by PID. Then verify every port is free and that each worktree still holds its branch and HEAD. A stack started by a legacy `screen` path writes no slot record, so the registry can read empty while ports are busy and later acquires fail closed on "foreign listener"; compare the registry against live listeners, and when they disagree append one truthful record for the live stack rather than stopping it — write it only after proving each PID is alive, inside the named run's scope, that run non-terminal, and the ports matching the slot (`memory-capped-job-execution` §6 carries a re-runnable `scripts/register_foreign_slot.py` for the verified write), and report the acquire-side gap as its own card, because a start path that forgets to record will blind the registry again. An orphan worktree with no card cannot pass the cleanup wrapper, which resolves cards from the board: preserve its branch on origin, record it, and report reclaiming card-less orphans as a missing supported operation.
- **Do not reverse your own scope or severity call without saying so.** When you relay a severity policy, classify the open findings once and hold that classification. A later note demanding restoration of an item you already classified as non-blocking reads to the worker and reviewer as conflicting authority, and the reviewer must then escalate a scope conflict for a human to resolve — a gate your own contradiction created. If a reversal is genuinely required, name the earlier note and state that this supersedes it.
- **Do not compare a merged squash against the reviewed head to check scope.** `git diff <reviewed-head> <squash>` is non-empty whenever the target branch advanced, and the unrelated commits it lists read as a scope violation. Compare like for like: merged delta `git diff --stat $(git rev-parse <squash>^) <squash>` versus reviewed delta `git diff --stat $(git merge-base <squash>^ <reviewed-head>) <reviewed-head>`. Equal file counts and insertion/deletion stats prove the merged content is the reviewed content; then confirm the squash is an ancestor of the target.
- **A fix card created with the card that needs the fix as its `--parent` inverts the ordering.** `--parent <id>` makes the NEW card wait on `<id>`, so filing a defect card against the card whose merge depends on that defect creates a circular dependency: the repair waits for the repair. Leave `--parent` off unless the new card genuinely waits on the named card, and carry precedence in `--priority` plus a comment instead. Repair an inverted edge with `kanban_db.unlink_tasks(conn, parent, child)` then `recompute_ready`, because leaving it parks the fix behind the card waiting for it; expect a reviewer to flag it as a circular order.
- **Never assert a code or artifact state in a routing comment without reading that head first.** A confident "you already reverted X" that the diff contradicts sends the implementer down a wrong path and costs a review round — and when the worker had done the right thing, the claim misdirects it into undoing correct work. Verify the claim against the exact head, and when the record is already wrong, post the correction yourself rather than making the worker reconcile it.
- **An operator comment can arm the guard it is trying to clear.** See the `active_pr` pitfall above: a decision, correction, or guidance comment that cites the PR URL re-arms the guard, so the card you just told to resume is not respawned. Name it as `PR #<n>`, or lift it with a genuine cross-profile `reassign` round-trip.
- **A read-only guard that blocks hash utilities prevents plan-digest verification.** When an orchestrator or planner must verify an approved plan's SHA-256 before graph reconciliation or card creation, `read_file` and `kanban_attachments` do not compute or expose cryptographic digests. If the profile's read-only execution guard permits only git/gh/kanban subcommands, the worker cannot verify the file hash independently and blocks as `capability` (`BLOCKED — MACHINE`). Ensure the profile's read-only allowlist explicitly permits deterministic hashing utilities (`sha256sum`, `shasum`) with path and secret guards, rather than treating digest verification as an unrecoverable capability block or expecting the worker to bypass the guard.

## Verification checklist

- [ ] Every non-terminal card assigned to a gate class, or named as an agent lane.
- [ ] Each reported gate carries the recorded reason, whether it still holds, and the exact next action.
- [ ] No gate claimed from a status column alone.
- [ ] Leaked fixture cards excluded from the gate count and named with their source.
- [ ] Alert silence never reported as "no gates".
